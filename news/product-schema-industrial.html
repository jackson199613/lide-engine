Product 结构化数据怎么写？工业品参数页 JSON-LD 示例（2026）

Product 产品结构化数据，就是在产品页里用 JSON-LD 把「这是什么产品、谁生产、关键参数是多少、单位是什么」写成机器可直接读取的字段。对工业品来说，写法的重点不是价格和评分，而是把 TDS 里决定选型的参数逐项放进 additionalProperty，并保证每个数值、单位都和页面上的 HTML 参数表一字不差。下面用一个消光粉参数页做示例，把字段、单位代码、常见错误和检查方法一次讲清。

要点速览
  • Google 建议优先使用 JSON-LD 格式，直接写在页面 HTML 里，不依赖前端脚本生成。
  • 工业品参数用 additionalProperty + PropertyValue 表达：名称、数值或范围、单位分开写。
  • 单位优先用 UN/CEFACT 通用代码（如 KGM 千克、P1 百分比），没有合适代码时用 unitText 写明。
  • 没有公开价格就不要硬写 offers，更不能编造评分或评价；参数可读比富媒体摘要更重要。
  • 结构化数据里的每个数字都必须在页面正文可见，并与 TDS 版本一致。

工业品页面为什么要单独写 Product 结构化数据？

海外买家问 AI 的方式越来越像选型：要什么体系、什么粒径、什么认证、多少起订量。AI 回答这类问题时，需要从网页里准确取出「参数名—数值—单位」三件套。很多工厂的参数只存在于 PDF 版 TDS 或一张图片里，人能看懂，程序却很难稳定解析。

Product 结构化数据解决的是「可读性」这一层：它不保证排名，也不保证被 AI 推荐，但能让搜索引擎和各类抓取程序少猜一步，知道这张页面描述的是哪个型号、由哪家工厂生产、关键指标是多少。我们在GEO 方法论里把它归为第一项能力「语义重塑」，因为后面的外部语料、型号对标都要以这层准确的产品实体为基础。

一个工业品参数页的 JSON-LD 应该长什么样？

下面是一个二氧化硅消光粉产品页的示例。品牌、型号和数值都是为演示虚构的，请换成你自己 TDS 上的真实数据。

{
  "@context": "https://schema.org",
  "@type": "Product",
  "@id": "https://www.example.com/products/mx-200#product",
  "name": "MX-200 水性涂料用二氧化硅消光粉",
  "sku": "MX-200",
  "mpn": "MX-200",
  "category": "涂料助剂 > 消光剂",
  "description": "适用于水性木器漆的沉淀法二氧化硅消光粉，经有机表面处理。",
  "image": "https://www.example.com/img/mx-200.webp",
  "url": "https://www.example.com/products/mx-200",
  "brand": {
    "@type": "Brand",
    "name": "ExampleChem"
  },
  "manufacturer": {
    "@id": "https://www.example.com/#organization"
  },
  "additionalProperty": [
    {
      "@type": "PropertyValue",
      "name": "SiO2 含量（干基）",
      "minValue": 98,
      "unitCode": "P1",
      "unitText": "%"
    },
    {
      "@type": "PropertyValue",
      "name": "平均粒径 D50",
      "minValue": 5.5,
      "maxValue": 7.0,
      "unitText": "µm",
      "measurementTechnique": "激光粒度法"
    },
    {
      "@type": "PropertyValue",
      "name": "pH（5% 水悬浮液）",
      "minValue": 6.0,
      "maxValue": 8.0
    },
    {
      "@type": "PropertyValue",
      "name": "适用体系",
      "value": "水性木器漆、水性工业漆"
    },
    {
      "@type": "PropertyValue",
      "name": "包装规格",
      "value": 10,
      "unitCode": "KGM",
      "unitText": "kg/袋"
    }
  ],
  "subjectOf": {
    "@type": "DigitalDocument",
    "name": "MX-200 TDS",
    "encodingFormat": "application/pdf",
    "url": "https://www.example.com/docs/mx-200-tds.pdf"
  }
}

这段代码放在产品页的 <script type="application/ld+json"> 里即可。几处值得注意的写法：

  • 范围值用 minValue / maxValue：TDS 常写「5.5–7.0 µm」，拆成上下限两个数字，而不是写成一个字符串，程序才能做数值比较。
  • 单下限用 minValue：「≥98%」只写 minValue，不要擅自补一个上限。
  • 测试方法写进 measurementTechnique：粒径、粘度这类结果依赖测试方法，写明方法能减少被误读。
  • manufacturer 指向 Organization 的 @id：全站只定义一次公司实体，各产品页引用同一个 @id，让「这个型号属于这家工厂」的关系前后一致。
  • TDS 用 subjectOf 关联：PDF 依然保留供下载，但关键参数已经在 HTML 和结构化数据里各出现一次。

哪些字段是必填，哪些对工业品最有用？

需要区分两个目标。如果你想在 Google 搜索结果里出现产品富媒体摘要，Google 的产品摘要文档要求至少有 name，并在 review、aggregateRating、offers 三者中提供其一；带购买功能的商家页面还另有一套商家信息要求。如果你的目标是让 AI 和搜索引擎读懂产品，那么参数类字段反而是重点。

字段作用工业品写法建议
name产品名称型号 + 品类 + 关键用途，和页面 H1 保持一致
sku / mpn型号与制造商零件号写对外公布的牌号或料号，不要用内部 ERP 编码
brand / manufacturer品牌与生产方manufacturer 引用全站唯一的 Organization 实体
category品类归属用买家熟悉的品类层级，避免内部分类名
additionalProperty技术参数每个关键选型指标一条 PropertyValue，数值与单位分开
hasCertification产品认证schema.org 已提供该属性；也可先用 PropertyValue 写认证类型与编号
offers价格与供货有真实公开价格再写；询价制产品可以不写
review / aggregateRating评价与评分只能来自真实、可核验的评价，宁缺毋编

参数的单位到底该怎么写？

schema.org 的 unitCode 建议使用 UN/CEFACT 通用代码，这是一套国际贸易里通行的计量单位代码，比如 KGM 表示千克、MMT 表示毫米、CEL 表示摄氏度、P1 表示百分比。用标准代码的好处是，不同语言、不同写法（kg、Kg、公斤）最终都指向同一个单位。

遇到「g/100g」「mPa·s」这类组合单位，或者一时找不到对应代码，不要硬套一个相近的代码，直接用 unitText 写清楚即可。原则只有一个：宁可表达朴素，也不能表达错误。单位写错的参数，比没有参数更伤可信度。

同一型号有多个规格，怎么写？

工业品常见「同一牌号、不同粒径或包装」的情况。两种做法：

  • 差异只在包装或小参数：保留一个 Product，在 additionalProperty 里列出可选规格即可。
  • 每个规格都有独立料号和独立参数：可以用 Google 在 2024 年起支持的产品变体写法，用 ProductGroup 作为父级，通过 hasVariant 列出各个 Product，用 variesBy 说明按什么维度区分。

不论哪种，关键是每个规格都能在页面上找到对应的参数行，不要让结构化数据里出现页面上看不到的规格。

工厂最常犯的 5 个错误是什么？

  1. 结构化数据和页面内容不一致：TDS 改版后只更新了 PDF，JSON-LD 里还是旧数值。Google 的结构化数据通用准则要求标记内容应能在页面上被用户看到。
  2. 参数塞进 description 一大段：所有指标写在一句话里，程序无法把数值和指标对应起来。
  3. 为了富媒体摘要编造评分：既违反规则，也会在买家核实时直接失去信任。
  4. 只靠前端脚本注入：Google 的产品文档提醒，用 JavaScript 动态生成的产品标记可能让抓取频率和可靠性下降，能写进初始 HTML 就写进初始 HTML。
  5. 每个产品页各写一套公司信息：公司名称、地址在不同页面写法不一，削弱了实体一致性。

写完之后怎么检查？

建议按这个顺序过一遍：先用 Schema Markup Validator 检查语法和类型是否符合 schema.org；再用 Google 富媒体搜索结果测试看是否有错误或警告；上线后在 Search Console 的网址检查里确认 Google 抓到的是最新版本。最后，人工抽查 3–5 个参数，确认 JSON-LD、HTML 参数表、TDS 三处数值完全一致。具体的 TDS 参数 HTML 化步骤，可以参考操作指南里的分步说明；想知道 ChatGPT 这类工具还会看哪些信号，可以读ChatGPT 是怎么推荐供应商的。

结语：先把 Top 3 产品的参数页写对

不必一次改完全部 SKU。先挑询盘最多、参数最关键的 3 个产品，把参数表 HTML 化、补上 Product JSON-LD、核对一遍数值，再按同一模板铺开。改之前可以先用 GEO 自查工具给官网打个分，或者申请一份免费的 AI 能见度诊断，看看 AI 现在复述你的产品参数时到底准不准。

常见问题

问：B2B 产品没有公开价格，还能用 Product 结构化数据吗？
答：能。schema.org 的 Product 并不强制要求价格，询价制产品可以只写名称、型号、品牌与参数；只是没有 offers、review 或 aggregateRating 时，通常无法获得 Google 的产品富媒体摘要。

问：JSON-LD 和 Microdata 选哪个？
答：优先选 JSON-LD。Google 建议使用 JSON-LD，它与页面 HTML 分开维护，改参数时不容易破坏页面结构。

问：加了 Product 结构化数据，AI 就会推荐我的产品吗？
答：不会自动推荐。结构化数据只是让产品参数更容易被准确读取，是否被推荐还取决于外部来源的交叉印证、内容与买家问题的匹配度等因素。

问：可以在结构化数据里写竞品型号来做替代对标吗？
答：要谨慎。只有在参数确实可比、并在页面上给出对照依据时，才适合用 isSimilarTo 之类的关系或正文对照表说明，不应借用他人商标制造误导。

问：参数改版后结构化数据要同步改吗？
答：必须同步。TDS、HTML 参数表和 JSON-LD 三处应在同一次发布中一起更新，否则数值不一致会削弱可信度。
