TDS 在线化：把 PDF 搬进 HTML，让 AI 读懂参数

技术数据表 TDS 在线化，就是把参数从 PDF 搬进 HTML：为每个牌号建一张独立网页，用真正的 HTML 表格逐行写出「参数名—数值—单位—测试方法」，PDF 保留为下载附件。这样做的原因很直接：AI 回答买家的选型问题时，需要从网页里准确取出参数，而 PDF 尤其是扫描件和图片版，最容易被读错、读漏或读不到。下面讲清楚 PDF 的具体问题、一张合格的 HTML 版 TDS 页该有哪些部分，以及从现有 PDF 迁移的步骤。

要点速览
  • Google 能索引 PDF，但 PDF 需要专门解析器提取文字；扫描版、图片版 TDS 基本等于没有文字。
  • HTML 版 TDS 的核心是一张带表头的参数表：参数、典型值或范围、单位、测试方法分列。
  • 一个牌号一个网址，页面写明 TDS 版本号与更新日期，并与 PDF 数值保持一致。
  • PDF 不删除，作为下载附件保留；HTML 页是给人和机器读的「主版本」。
  • 结构化数据是下一步，先把 HTML 参数表做对，再加 Product JSON-LD。

TDS 放在 PDF 里，AI 为什么读不准？

先说清楚：PDF 并非完全不能被读取。Google 的官方文档把 PDF 列在可索引的文件类型里，同时说明这类文件属于需要专门解析器提取文字的二进制或复杂容器。问题出在「解析」这一步，工业品 TDS 恰好是最难解析的那类文档：

  • 扫描件和图片版：很多工厂的 TDS 是盖章后扫描的，页面上全是图片，没有可选中的文字。行业媒体对 Google《Search Off the Record》播客的转述也提到，纯图片 PDF 是问题，不宜依赖 OCR。一个简单自测：打开你的 TDS，试着选中一行参数复制到记事本，复制不出来，机器大概率也读不出来。
  • 多栏排版和合并单元格：TDS 常把参数表排成两栏，或把「测试方法」合并到一列里。转成纯文本后，数值和参数名很容易错行，「粒径 5.5–7.0」可能被拼到「pH」后面。
  • 上下标与特殊符号：m²/g、µm、≥、±、D50 这类写法，在 PDF 文字层里常被拆散或替换成乱码。
  • 更新不及时：同一篇转述提到，静态 PDF 可能被重新抓取得较慢，Google 没有承诺固定的更新周期。TDS 改版后，旧数值可能还在被引用。
  • 没有上下文：一个孤零零的 PDF 链接，没有页面标题、没有品类说明、没有和公司实体的关系，AI 很难判断它属于谁、适用于什么场景。

结论是：PDF 适合打印和存档，不适合作为参数的唯一载体。买家问 AI「哪家供应商有比表面积 200 m²/g 左右的气相二氧化硅」时，参数能不能被准确取出，决定了你能否进入候选名单。

一张合格的 HTML 版 TDS 页面，应该包含哪些部分？

不需要花哨的设计，需要的是结构清楚、信息完整。我们建议每个牌号的页面至少包含以下几块：

页面模块写什么常见错误
H1 标题完整牌号 + 品类 + 主要用途，如「XX-200 水性木器漆用消光粉」只写牌号，或只写品类不写牌号
导语段两三句话说明这是什么产品、适用于什么体系、核心优势是哪一两个参数写成公司简介或营销口号
参数表参数名、典型值或范围、单位、测试方法（标准号）四列分开把参数表做成图片，或数值和单位挤在一个格子里
适用场景推荐体系、推荐添加量、不建议使用的场景只写「广泛适用」
认证与合规已取得的认证、证书编号或可提供的文件类型写尚未取得的认证，或不写编号
包装与供货包装规格、储存条件、保质期、起订量（如愿公开）完全不写，迫使买家先询价
版本信息TDS 版本号、更新日期、PDF 下载链接HTML 与 PDF 数值不一致

其中参数表最关键。用真正的 <table>，第一行用 <th> 做表头。W3C 无障碍教程对数据表的建议同样适用于机器读取：表头单元格要明确标出，必要时用 scope 说明表头作用于行还是列，用 <caption> 给表格一个标题。屏幕阅读器能看懂的表格，程序通常也能看懂。

参数表具体怎么写，才算「AI 读得懂」？

把 PDF 里的表格原样搬过来还不够，有几条写法上的规则：

  • 数值和单位分开：「200 m²/g」拆成数值列「200」和单位列「m²/g」，范围写成「180–220」，单侧限写「≥ 98」，不要写「约 200 左右」。
  • 写典型值还是规格值，要说明：TDS 上的「Typical value」和 COA 上的「Specification」不是一回事，表头里写清楚，避免买家和 AI 把典型值当成保证值。
  • 测试方法写标准号：粒径、粘度、比表面积这类结果强依赖测试方法，写明对应的 ISO、ASTM 或国标编号，比单写「激光法」更可信。
  • 参数名用行业通用叫法：中文页写中文通用名，英文页用海外买家搜索时的英文术语，比如 BET specific surface area，不要用内部缩写。
  • 上下标用正确字符：m² 用上标字符或 <sup>，µm 用正确的微符号，不要用图片代替。

判断标准只有一个：把这张表复制粘贴到一个空白文档，每一行仍然能读出「什么参数、多少、什么单位、怎么测的」，就合格了。

从 PDF 迁移到 HTML，按什么顺序做？

工厂往往有几十上百份 TDS，不必一次全做。按下面的顺序推进，工作量可控：

  1. 先挑 3–5 个主推牌号：选询盘最多、利润最好或最想打开海外市场的型号。我们的操作指南里有一篇「如何把 TDS 里的参数改造成 AI 可读的结构化数据」，可以配合阅读。
  2. 确认每份 TDS 是最新版：和技术部核对版本，删掉已停产或参数已变更的旧文件。迁移是清理数据的好机会。
  3. 提取参数并人工核对：可以用工具或 AI 辅助把 PDF 表格转成文字，但每个数字都要由懂产品的人逐项核对，尤其是范围值、单位和小数点。
  4. 建页面模板：按上面的模块做一个统一模板，后续牌号只换内容。一个牌号一个固定网址，网址里带牌号，例如 /products/xx-200。
  5. 挂上 PDF 下载并标注版本：HTML 页面底部放 PDF 下载链接，两边写同一个版本号和日期。
  6. 加结构化数据：HTML 参数表确认无误后，再用 Product 和 PropertyValue 把参数标记一遍，写法见《Product 结构化数据怎么写》。
  7. 检查能否被抓取：确认 robots.txt 没有屏蔽 AI 爬虫，页面不需要登录或填表才能看到参数。

HTML 页面和结构化数据是什么关系？

两者不是二选一。HTML 参数表是给人看、也给机器看的「正文」；结构化数据是在同一页面里，用 Schema.org 的词汇把这些参数再标注一次。Schema.org 的 PropertyValue 类型提供了 value、minValue、maxValue、unitCode、unitText 等属性，其中 unitCode 建议使用 UN/CEFACT 三位通用代码。

顺序很重要：先有正确的 HTML，再有结构化数据。结构化数据里的每一个数字，都必须能在页面正文里看到，并且与 TDS 当前版本一致。如果 HTML 表格还是图片、或者数值前后矛盾，加再多标记也没有意义。这也是我们在GEO 方法论里把「语义重塑」放在第一步的原因：后续的外部语料和型号对标，都建立在产品参数准确可读的基础上。

做完之后，怎么判断有没有用？

TDS 上网是基础动作，它提高的是「被读懂」的可能，不保证排名，也不保证被 AI 推荐。可以从三个方面检查：

  • 可读性：用 Google Rich Results Test 和 Schema.org Validator 检查结构化数据没有报错；复制参数表到纯文本，确认不乱行。
  • 收录：在 Google Search Console 里查看这些牌号页是否已被编入索引。
  • 引用：每月用固定的选型问法，在 ChatGPT、Perplexity、Gemini 等平台提问，记录是否出现你的牌号、引用的是 HTML 页还是 PDF、数值是否正确。

常见问题

问：TDS 改成 HTML 之后，PDF 还要保留吗？
答：要保留。PDF 方便买家下载、打印和归档，HTML 页面负责被人和机器在线读取，两者写同一个版本号和更新日期，数值保持一致即可。

问：扫描版 TDS 加上 OCR 文字层就够了吗？
答：不够稳妥。OCR 容易把单位、小数点和上下标识别错，而且 PDF 依然缺少页面上下文；更可靠的做法是把参数人工核对后写进 HTML 表格。

问：参数涉及配方机密，能不能不全公开？
答：可以。只公开买家用来筛选和比对的选型参数即可，比如粒径、纯度、比表面积、认证；配方组成、工艺参数等不需要上网。

问：中英文 TDS 页面要分开做吗？
答：建议分开。每种语言一个独立网址，参数名用该语言的行业通用术语，数值和单位两边完全一致；海外买家主要用英文提问，英文页优先级更高。

问：做一张 HTML 版 TDS 页要多久？
答：有模板之后，单个牌号的参数提取、核对和上线通常以小时计，最花时间的是和技术部核对数据，而不是页面制作本身。
